# LinkAja Applink (SNAP): specification summary

**Compiled:** 2026-09-28, **revised 2026-10-01** against the official specification PDF.
**Sources:** the spec PDF (v1.1) and LinkAja's credential pack. Both are kept outside the repo and are
not committed.

Each item cites its source. Where the Postman collection (dated 2026-09-01) and the PDF (2025-05-08) disagree,
**the PDF wins** and the code follows the PDF. Anything in neither is marked **NOT IN DOCS**. A few facts were
*observed* from the LinkAja dev sandbox; those are labelled **OBSERVED (sandbox)** with the date.

> No secrets appear in this file. Credential values live only in the local, gitignored `.env`.

## 3. Authentication

### 3.1 Access token (asymmetric). [PDF] §4.1, §5.1.1

`POST /bi/v1.0/access-token/b2b`, service code 73.

| Header | Value |
|---|---|
| `X-TIMESTAMP` | ISO 8601 `YYYY-MM-DDThh:mm:ssTZD` ([PDF] §5.1.6); we send Jakarta time `+07:00` |
| `X-CLIENT-KEY` | Clientkey |
| `X-SIGNATURE` | `base64( SHA256withRSA( privateKey, "<clientKey>|<X-TIMESTAMP>" ) )` |

Body: `{"grantType": "client_credentials"}`

Response ([PDF] p.9-10): `responseCode` `2007300`, `responseMessage`, `accessToken`, `tokenType` `Bearer`,
`expiresIn` **"900" seconds (15 minutes)**; sandbox reports `"899"`. The code caches the token and refreshes it
60 s before expiry; a `401` on a service call drops the cache and retries once.

### 3.2 Service calls (symmetric). [PDF] §5.1.2, §5.1.5

```
stringToSign = METHOD + ":" + EndpointUrl + ":" + accessToken + ":" + lowercase(hex(SHA256(minify(body)))) + ":" + X-TIMESTAMP
X-SIGNATURE  = base64( HMAC-SHA512( Secretkey, stringToSign ) )
```

`EndpointUrl` is the request path, e.g. `/bi/applink/v1.0/debit/status`. We serialize the body compactly once
and hash and send those exact bytes.

| Header | Value |
|---|---|
| `Authorization` | `Bearer <accessToken>` |
| `X-TIMESTAMP`, `X-SIGNATURE` | as above |
| `X-PARTNER-ID` | Partner-ID |
| `X-EXTERNAL-ID` | numeric string, unique within the day |
| `CHANNEL-ID` | `<channel-id>` |
| `Origin` | optional, not sent |
| `User-Agent` | `ios` on create payment ([PM-PAY] only; not in [PDF]) |

## 4. APIs

### 4.1 Create Applink Payment. [PDF] §4.2 (p.10-13), service code 54

`POST /bi/applink/v1.0/debit/payment-host-to-host`

| Field | M/O | Notes |
|---|---|---|
| `partnerReferenceNo` | M | our `user_order.id` |
| `merchantId` | M | |
| `terminalId` | O | |
| `amount.value` / `amount.currency` | M | `"NNNN.00"` string, `IDR` |
| **`urlParams[]`** `.url` / `.type` / `.isDeeplink` | M | **plural** (v1.1 rename, p.2); `type` **`PAY_RETURN`**; `isDeeplink` `Y`/`N`. One entry. LinkAja confirmed its `url` is **our notify URL** (`LINKAJA_NOTIFY_URL`), `isDeeplink` `N`. |
| `additionalInfo.trxDate` | M | `YYYYMMDDHHMMSS` |
| `additionalInfo.terminalName` | O | |
| `additionalInfo.items[]` `.id` / `.name` / `.unitPrice` / `.qty` | M | `id` unique per `partnerReferenceNo` |

Response (p.12-13): `responseCode` `2005400`, `responseMessage`, `appRedirectUrl` (M), `referenceNo`
(conditional, LinkAja's reference).

**Postman vs PDF:** [PM-PAY] sends `urlParam` / `partnerApplink`. The sandbox accepts both
(OBSERVED 2026-09-28 and 2026-10-01). The code sends the PDF form.

**Notify URL:** the PDF has no dedicated field. LinkAja confirmed (2026-10) that the notify URL goes in
`urlParams[0].url`, type `PAY_RETURN`, `isDeeplink` `N`. The code sends `LINKAJA_NOTIFY_URL` there.

OBSERVED (sandbox): a UUID `partnerReferenceNo` is accepted; a duplicate `partnerReferenceNo` is accepted and
yields a second `referenceNo` (the [PDF] §5.2 `409xx01 Duplicate partnerReferenceNo` applies once the first one
succeeded).

### 4.2 Applink Inform Payment (notify). [PDF] §4.3 (p.14-16), service code 56

Invoked **by LinkAja to us**, `POST …/bi/applink/v1.0/debit/notify` (the host part is ours). We serve that
exact path and `POST /api/v1/callback/linkaja`, same handler.

Headers: `X-TIMESTAMP`, `X-SIGNATURE` (see §5.1.3 below), `X-PARTNER-ID`, `X-EXTERNAL-ID`, `CHANNEL-ID`. No
`Authorization`.

Body: `originalPartnerReferenceNo` (our order id), `originalReferenceNo` (LinkAja's), `merchantId`,
`latestTransactionStatus` ("LinkAja will inform payment to partner with value 00"), `amount{value,currency}`,
`createdTime`, `finishedTime`, `additionalInfo{approvalCode, terminalId, terminalName, items[]}`. The p.16 sample
sends `amount.value` `"6000"` **without** decimals, although p.14 says two decimals; the code accepts both.

Expected response (p.15-16), exactly:

```json
{"responseCode":"2005600","responseMessage":"Successful","approvalCode":"<approvalCode from the request>"}
```

**Flow (p.7 diagram):** LinkAja reserves the payment, informs us ("with pending status" in the diagram, `00` in
the text), waits for our ack, **then commits** the transaction and pushes a notification to the customer. So our
handler must answer quickly: verify, record, ack; eSIM provisioning runs after the response.

**NOT IN DOCS:** what happens if we do not answer or answer with an error (reversal? retry count and interval?);
timeout for our response; whether the notify is signed with LinkAja's own key or the pair LinkAja gave us.

### 4.3 Applink Inquiry Status. [PDF] §4.4 (p.17-18), service code 55

`POST /bi/applink/v1.0/debit/status`

Body: `originalPartnerReferenceNo`, **`serviceCode` `"55"`** ([PM-STATUS] sends `"54"`), `merchantId`,
`additionalInfo.terminalId`.

Response (p.18): `responseCode` `2005500`, `originalPartnerReferenceNo`, `originalReferenceNo`, `approvalCode`,
`serviceCode`, `latestTransactionStatus` (see §6), `transactionStatusDesc`.

OBSERVED (sandbox, 2026-09-28 and 2026-10-01): a created-but-unpaid payment answers HTTP **404**
`{"responseCode":"4045501","responseMessage":"Transaction Not Found"}`, with `serviceCode` 54 and 55 alike. The
code treats that as **NOT_FOUND = not paid yet** and leaves the order pending. A successful inquiry response has
not been observed.

### 4.4 Applink Refund. [PDF] §4.5 (p.19-22), service code 58

`POST /bi/applink/v1.0/debit/refund`. Body: `originalPartnerReferenceNo`, `partnerRefundNo`, `merchantId`,
`refundAmount{value,currency}`, `additionalInfo{approvalCode, terminalId (O), refundType 1=full / 2=partial,
items[{id, qty}]}`. `approvalCode` comes from the notify or the inquiry response. Response code `2005800`,
`refundNo`, `refundTime` (ISO 8601). Max refund period: `405xx01 Requested Operation Is Not Allowed` (p.25),
length **NOT IN DOCS**. **Not implemented** in the service.

## 5. Signatures. [PDF] §5.1

- **§5.1.1 token:** `base64(SHA256withRSA(privateKey, clientId + "|" + timestamp))`.
- **§5.1.2 transaction request:** `base64(HMAC_SHA512(clientSecret, METHOD:EndpointUrl:AccessToken:lowerhex(sha256(minify(body))):timestamp))`.
- **§5.1.3 debit notify (inbound):**
  `base64(SHA256withRSA(privateKey, METHOD:EndpointUrl:lowerhex(sha256(minify(body))):timestamp))` - no access
  token component. We verify with LinkAja's public key (`LINKAJA_NOTIFY_PUBLIC_KEY[_PATH]`). **Key not received
  yet** → every notify is rejected (fail closed).
- **§5.1.5 minify:** strip `\r`, `\n`, `\t` and spaces. Ambiguous for spaces inside JSON strings; the verifier
  tries the raw bytes, compact JSON and the fully stripped form.
- **EndpointUrl for the notify:** not pinned (full URL or path?). Default: the path LinkAja called; override with
  `LINKAJA_NOTIFY_ENDPOINT_URL`.
- **§5.1.6 timestamp:** ISO 8601 with `Z` or `±hh:mm`.

## 6. Status codes and vocabulary

**Transaction status** ([PDF] §5.4, p.25, complete list): `00` Success, `04` Refunded, `06` Failed, `07` Not
Found. There is **no pending/expired status**; an unpaid transaction is "Not Found".

**Response codes** ([PDF] §5.2, p.24-25; `xx` = service code):

| Code | Meaning |
|---|---|
| `200xx00` | Successful |
| `400xx00` / `400xx01` / `400xx02` | Bad Request / Invalid Field Format {field} / Invalid Mandatory Field {field} |
| `401xx00` / `401xx01` | Unauthorized. [reason] / Invalid Token (B2B) |
| `404xx01` / `404xx08` / `404xx13` | Transaction Not Found / Invalid Merchant / Invalid Amount (items ≠ total) |
| `405xx01` | Requested Operation Is Not Allowed (max refund period exceeded) |
| `409xx01` | Duplicate partnerReferenceNo (already success) |
| `500xx00` / `500xx01` | General Error / Internal Server Error (retry) |
| `504xx00` | Timeout |

The notify route answers with these for service code 56: `2005600` success, `4015600` invalid signature,
`4045601` unknown order, `4045608` wrong merchant, `4045613` amount mismatch, `4005602` missing field,
`5005601` not configured (retry later).

## 7. Currency and amount

- Currency: `IDR` only ([PDF], [PM-*]).
- Format: decimal string with two places, e.g. `"29880.00"` (p.11); the notify sample uses `"6000"` (p.16).
- USD→IDR conversion: **business decision**, `LINKAJA_USD_TO_IDR_RATE`. The IDR amount and the rate used are
  stored on the order at creation (inside `bundle_data`, key `linkaja_payment`) and the notify is reconciled
  against that stored amount, so the rate can change while payments are in flight.
